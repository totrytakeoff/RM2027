# Referee 模块 2026 协议对齐现状记录

文档目的：

1. 记录当前 `components/devices/referee` 已落地功能与边界。
2. 对照 `RoboMaster 2026 通信协议 V1.2.0（20260209）` 明确差异项。
3. 为后续迭代提供统一事实基线，避免重复排查。

更新时间：2026-03-12

---

## 1. 当前结论（摘要）

当前裁判系统模块已达到“**基本可用**”状态，主要表现为：

1. 裁判串口接收/校验/解析链路可运行。
2. 关键高频状态数据已按 2026 协议口径完成更新并可存入 `referee_info_t`。
3. UI 与 0x0301 机器人交互链路可发送。
4. 仍存在若干未闭环点（见第 4 节），其中有高优先级项需尽快补齐。

---

## 2. 已明确实现落地的能力

### 2.1 接收链路基础能力

文件：`components/devices/referee/rm_referee.c`

1. SOF 校验（`0xA5`）
2. 帧头 CRC8 校验
3. 帧尾 CRC16 校验
4. 基于 `data_length` 的帧长计算（已改为 16-bit 正确解析）
5. 多帧粘包递归解析（已增加边界保护）
6. daemon 掉线检测与串口重启

### 2.2 已接入解析的命令字

已在 `switch(cmd_id)` 中落地解析并写入 `referee_info_t`：

1. `0x0001` 比赛状态
2. `0x0002` 比赛结果
3. `0x0003` 机器人血量（己方视角）
4. `0x0101` 场地事件
5. `0x0104` 裁判警告
6. `0x0105` 飞镖发射相关
7. `0x0201` 机器人状态
8. `0x0202` 功率/热量
9. `0x0203` 机器人位置
10. `0x0204` 增益
11. `0x0206` 受伤
12. `0x0207` 射击数据
13. `0x0208` 允许发弹量
14. `0x0209` RFID 状态
15. `0x0301` 机器人交互数据

### 2.3 已更新的数据结构口径（关键）

文件：`components/devices/referee/referee_protocol.h`

已完成对齐的关键项：

1. `game_state` 扩展到 11 字节（含 `SyncTimeStamp`）
2. `game_robot_HP` 修正为 16 字节己方视角结构
3. `game_robot_state` 修正为 13 字节新结构
4. `game_robot_pos` 修正为 12 字节（`x,y,angle`）
5. `buff` 修正为 8 字节新结构
6. 新增 `referee_warning/dart_info/projectile_allowance/rfid_status` 结构

## 3. 本轮已修复的关键问题（防故障）

1. `0x0003` 长度宏历史错误（旧值 `2`）已改为 `16`。
2. 帧长计算从低字节读取改为 16-bit 合并读取，防止误判长度。
3. 多帧递归偏移改为使用已校验的 `judge_length` 并加边界判断，降低越界风险。
4. `robot_id` 红蓝判定条件已从旧逻辑调整为 2026 口径（蓝方 > 10）。

---

## 4. 与新版仍存在的差异（按重要性）

### 4.1 高重要性

1. **客户端 ID 映射仍未按 2026 固定表实现**
   1. 现状：`referee_task.c` 使用 `0x0100 + robot_id` 线性计算。
   2. 风险：蓝方客户端 ID 可能错误，导致 UI/交互目标不正确。

2. **裁判反馈对控制环未形成闭环**
   1. 现状：`chassis.c` 中功率/热量/弹速限制仍为注释占位。
   2. 风险：解析到了数据但控制不受约束，实战中可能出现超限与策略失效。

### 4.2 中重要性

1. **`0x020A~0x020E` 未完成 payload 结构与解析分支**
   1. 现状：已定义 cmd 枚举，但未在 `referee_info_t` 和 `switch` 完整落地。
   2. 风险：飞镖/雷达/哨兵相关功能扩展受限。

2. **`RefereeSend` 固定延时 115ms**
   1. 现状：发送节流策略较旧，约 8.7Hz。
   2. 风险：不利于发挥 2026 交互上限（如 `0x0301` 上限 30Hz）。

3. **`Robot_ID_e` 枚举仍是旧版蓝方 101~109 编号**
   1. 现状：与 2026 文档 11~19 不一致。
   2. 风险：后续若该枚举被复用，会引入目标ID错误。

### 4.3 低重要性

1. 协议注释存在少量旧描述（如部分 Byte 注释未完全同步）。
2. 文档级说明与代码行为有零散不一致，影响维护理解但不直接影响运行。

## 5. 当前可支持的典型使用场景

1. 正常接收并读取比赛基础状态、机器人状态、热量与增益信息。
2. 基于 `0x0301` 进行 UI 图元下发与机器人交互数据传输。
3. 单板工程中完成裁判链路在线检测与自动恢复。

不建议当前直接依赖的场景：

1. 对蓝方客户端 UI 目标地址要求严格的场景（先修 ID 映射）。
2. 依赖 `0x020A~0x020E` 的雷达/飞镖/哨兵策略联动场景。
3. 依赖裁判限额做强约束的控制闭环场景（先接入控制层限幅）。
